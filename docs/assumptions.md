# InspectIQ — Assumptions & Limitations

This document lists all assumptions made by the system and their rationale.

## Data Assumptions

### 1. Schema Mapping
- **Assumption**: The provided dataset can be mapped to the internal schema via `configs/schema_mapping.yaml`.
- **Action required**: Edit the YAML file to match actual column names.
- **Impact if wrong**: Ingestion fails; data quality report will show missing required fields.

### 2. Normal/Defective Labels
- **Assumption**: The `inspection_result` column contains the ground-truth label ("good" / "defective") for vision engine training.
- **Fallback**: If labels are absent, the system assumes all training images are normal and uses unsupervised anomaly detection only.

### 3. Defect Family Labels
- **Assumption**: The `defect_family` column identifies the defect type.
- **Fallback**: If absent, defects are clustered into candidate families via HDBSCAN (unsupervised).

### 4. Process Parameters
- **Assumption**: Process parameters are linked to units via `unit_id` or (`batch_id`, `station_id`).
- **Fallback**: If no process data is available, root-cause analysis is limited to batch/station statistical tests.

## Model Limitations

### Vision Engine (Lightweight Backend)
- Uses scikit-learn Isolation Forest on process-parameter features (proxy for image features).
- When actual images are not available, anomaly detection operates on tabular data only.
- Heatmaps are model-generated approximations; they are **not validated against ground-truth pixel masks**.
- For production use, replace with Anomalib/PatchCore backend (set `vision.yaml: backend: patchcore`).

### Conformal Prediction
- Calibration guarantees assume test data is exchangeable with calibration data.
- Under strong distribution shift, coverage guarantees weaken.
- The dashboard monitors score distribution for staleness warnings.

### Root-Cause Hypotheses
- All outputs are **statistical hypotheses**, not proven causes.
- Confounding is listed explicitly for each hypothesis.
- Correlation ≠ causation. Process investigation is required before taking action.

### Flow Simulation
- SimPy simulation is calibrated to historical throughput and WIP.
- Simulation accuracy depends on how representative the calibration data is.
- All simulation outputs are labelled **SIMULATED / ADVISORY**.

### Recommendations
- All recommendations are labelled **SIMULATED / ADVISORY**.
- Expected impacts are estimated from simulation, not guaranteed.
- Recommendations should be reviewed by domain experts before implementation.

## Scope Limitations

- **No hardware control**: The system does not connect to PLCs, robots, or cameras.
- **Offline/replay only**: Processes pre-recorded datasets; not a real-time system.
- **Advisory only**: No automatic execution of recommendations.
- **Human-in-the-loop**: REVIEW and NOVEL cases are routed to human review.

## Supplementary Data Used for Development

The synthetic dataset (generated by `data/synthetic/generator.py`) is used for:
- Development and testing of all modules
- Demonstration of all system capabilities
- Evaluation of root-cause engine on known injected faults

Final results will be reported against the organizer-provided dataset.
